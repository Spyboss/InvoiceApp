## current step

step 10 (add a user) is **todo**. it exists because of a gap found while testing step 9, not as new scope: `store.CreateUser` is called only by `setup.go` (first run, and `users > 0` refuses a second) and by tests, while the `/users` routes change role, active state and password for rows that already exist. a tenant therefore holds exactly one account, and `docs/CUTOVER.md` requires "one staff member issued a real invoice unaided". the screen goes on `/users`, behind `user.manage`, reusing `auth.ValidatePassword` for the 12 character rule and writing `user.create` inside the same transaction, exactly as `setup.go` does for the first owner.

step 9 (interface frame) is **done**. D31 is the decision.

- the destinations left the header row for a left sidebar in three task groups — counter (Documents, Customers, Vehicles, Stock, Payments, Day end), oversight (Reports, Alerts, Reconciliation), admin (Import, Audit, Settings, Users) — read in the order `docs/COUNTER.md` walks a day. permission still decides which links exist, and a group whose links are all filtered out does not render: a SERVICE user sees one heading and three links, verified against a real session rather than read off the code.
- at 360px the sidebar becomes a wrapping row above the content, not a drawer, and `document.documentElement.scrollWidth === clientWidth` holds on every screen measured.
- a heading may carry one line, and only one that says something the heading cannot. two screens have one — `/payments` ("One receipt, one invoice.") and `/reconciliation` ("The old app's file against the papers held here.") — and the rest draw none, because a blank is never filled for symmetry. the line is `views.Note`, one component, so the styling and the rule live in one place.
- **the brand green had never applied.** pico declares `--pico-primary` on `:root:not([data-theme=dark])`, specificity (0,2,0), which beats a plain `:root` (0,1,0) whatever the load order; every button and link in the app rendered pico blue `#0172ad` instead of `#0b5d1e`. `:root` was byte-identical at HEAD, so this predates the step. the block is now `:root:root`, which ties and, loading second, wins.

the software side of step 8 is still the sequence to run rather than advice:

- `docs/CUTOVER.md` is the order: the old app's dump first, an empty production database, the app with `APP_ENV=production`, `/setup` finished before the domain is public, the settings that print on paper, and a checklist that step 8 is signed off against.
- `backup/` is a railway cron service that writes one dump a night to a volume on the other provider from the database, proves `pg_restore` can read it, and keeps 14 days (D29). the database itself keeps six hours of history on its current plan, which is why this exists.
- `scripts/backup.sh` refuses an empty book and refuses a role that cannot bypass rls, because every table that holds the book forces it and such a role dumps a file that is not the book. both guards were found the hard way: the drill had quietly stopped working after the last tables were locked.
- `docs/COUNTER.md` is the one page the counter gets: what each screen is for, in the order a day uses them.

what remains is his to do and all of it is on the checklist: a neon project, a railway production environment, the domain, and one staff member issuing a real invoice unaided. the parallel month that used to sit between steps 7 and 8 is dropped (D28): the owner deploys when the software is finished and tests on the live business, adjusting it as he goes.

step 7 is **done** on the software half, which is all D28 leaves it: imported totals match the csv source exactly, enforced by a constraint rather than by a comparison somebody has to remember to make.

- `/import`: two files, `invoices.csv` from the old app and the yard sheet. a good upload redirects to `/import?run=<id>` and the page reads the run back from the database. `import.run` is OWNER only.
- the import is one transaction and all or nothing: a file with one bad row is refused whole, every problem named on its line, and nothing is written. a second upload of the same file finds every number already held and writes nothing, so the same file is safe to send every day of the month.
- imported papers keep the number the old app printed (`documents.imported_at`, `documents.import_run_id`) and are never renumbered; the app's counters are lifted above every imported number for the year afterwards, cash and leasing sales sharing one series so a file that mixes both lifts a single counter (D26, D23).
- a `SALES` row with nothing owing is a cash invoice and one with a balance is a leasing sale; stock follows the paper (sale: `RECEIVE`+`SELL`, advance: `RECEIVE`+`RESERVED`, proforma: `RECEIVE` only). customers match on nic then name, units on chassis, so five years of paper does not become five hundred copies of the same person.
- the acceptance is a database constraint, not a screen: `import_runs` stores what the file claimed and what the database held, and `check (source_totals = stored_totals)` refuses a run that does not balance. `import_run_id` is a deferred foreign key because the papers are written before the run row, inside the one transaction.
- `/reconciliation`: upload the same file for a range of days and the store compares it with the papers that came in from a file, per day and per document type, keeping papers, price, down and balance apart. the difference and `matched` are generated columns, so a line cannot claim a match; a run that finds a difference writes a `RECONCILIATION` alert in the same transaction. `reconcile.run` is OWNER, MANAGER and ACCOUNTS.
- the two upload pages needed csrf middleware that reads multipart bodies; it now does, behind `http.MaxBytesReader` at 10 MB, and every upload is hashed with sha256 and stored with its run. `docs/IMPORT-FILES.md` is the column reference for both files and the reconciliation routine for a day when a number is in doubt.

step 7 acceptance, all of it testable: an upload writes the book and a repeat writes nothing; a file that does not add up is refused whole and the typed make kept; an upload with no csrf token is a 403; a salesperson gets 403 on both pages and accounts gets 403 on `/import`; a reconciliation that agrees records `matched`, one that drifts records the difference and raises an alert; bad dates are refused. the month of parallel running that D23 also asked for was dropped by D28, so nothing here waits on the counter.

step 7 also carried the interface pass (D24). all fifteen screens were rewritten against one frame and one voice: `Layout` now holds the dealership, the destinations, who is signed in and the sign-out form, so no page repeats them; taglines under headings, helper text under inputs and paragraphs explaining rules in advance are gone, and a constraint that mattered folded into its label ("Password (12 characters or more)"); facts are `dl.facts` rows or tables with headings; empty states are one line and say "none yet" differently from "no match"; the alert channels read as a fact ("this page only") rather than a warning. view fields no template drew were deleted rather than kept (home's `CanSeeAudit`, the alert's `Kind`, the import page's `Attempted`/`Notice`, the reports' `ReadAll`, a document's `IsQuote`), and the settings screen shows a read-only `dl.facts` view to anyone without `settings.write` instead of a disabled form. every page was measured at 360px: nothing scrolls sideways, and the wide tables scroll inside their own box with the cell padding gave up first. the stylesheet is now revalidated with an `ETag` and `no-cache` (D25) after a css rule was found to be serving from a browser cache.

step 6, for the record: `/settings` and `/users` are the owner's screens (company details, discount percent, variance threshold, backdate limit, alert email and telegram chat; list everyone, change a role, activate or deactivate, reset a password), each refusing anyone without the permission before it loads. a `users_keep_one_owner` trigger refuses removing the last active owner, and MANAGER no longer carries implicit `user.manage`. approval pins re-authenticate the approver's own password and check the effective `document.approve` permission, so a clerk cannot forge a sign-off. a void keeps the paper and its number, returns the unit to the yard, and writes an alert; alerts fire on void, variance and numbering gap, are insert-only, and leave by email and/or telegram when configured.

step 5, for the record: a receipt pays one named invoice and can never exceed what it still owes, in the store and in a database trigger. a receipt is inserted once; handing money back is a reversal dated the day it happens, so a counted day is never rewritten. money cannot be dated on a closed day, and a close is insert only, so a z cannot be edited by anyone. the z stores its totals and its lines as they were at close time, and exports as csv.

step 4, for the record: `/documents` issues quotations, cash and leasing invoices, advance receipts and proformas. numbers come from `document_series`, bumped in the same transaction as the document, so concurrent clerks never share one and a rollback leaves no gap. a sale sets the unit sold and writes the `SELL` movement in that transaction; a quotation converts once. printed fields are frozen by a database trigger, and the first pdf is archived with its sha256, so later downloads serve the same bytes. the proforma was compared against a libreoffice render of `BIBILE 01.docx`: the table and body agree within about 1pt.
